

#Behavioral Characterisation of LLM-generated Differential Evolution
Algorithms on Complex Landscapes

This repository contains the code, experimental data, and analysis pipelines used to study **how ten Differential Evolution (DE) variants generated by the LLaMEA framework actually behave** when optimizing the CEC2022 benchmark suite in 10 and 20 dimensions.

The work does **not** propose a new optimization algorithm. Its contribution is *behavioural explainability*: understanding how automatically generated optimizers explore, exploit, converge, and stagnate — information that conventional performance metrics cannot reveal.

## Overview

LLM-driven frameworks such as LLaMEA can now generate competitive optimization algorithms with minimal human involvement. However, these algorithms arrive without any documented account of their search logic, and their evaluation still relies almost entirely on performance metrics — best objective value, rankings, anytime measures. Such metrics answer *which* generated algorithm is better, but say nothing about *how* it searches.

This repository implements a four-layer analysis framework addressing that gap:

| Layer | Purpose | Instruments |
|---|---|---|
| **Generation** | Obtain algorithms without manual design | LLaMEA-generated DE variants |
| **Benchmarking** | Observe all variants under identical conditions | CEC2022 suite, IOHexperimenter logging |
| **Performance** | Quantify optimization quality over the full budget | AOCC, ERT, EAF/ECDF, heatmaps |
| **Explainability** | Explain *why* the differences arise | SHAP (3 levels), Search Trajectory Networks, behavioural metrics |

All analyses are derived from the same logged benchmark data, so performance outcomes, sensitivity structures, and search behaviours can be interpreted jointly.

## The Ten Generated Variants

All variants were produced by LLaMEA and are used **exactly as generated**, without manual modification of their search logic.

| # | Variant | Principal mechanism | Production configuration |
|---|---|---|---|
| 1 | `adeo` | DE/rand/1/bin with exponential decay of `F` and `CR` (×0.99 per generation) | NP=100, F=0.8, CR=0.9 |
| 2 | `de_crossover` | DE with adaptive crossover-rate control | NP=100, F=0.8, CR=0.7 |
| 3 | `de_gradient_boost` | Finite-difference gradient refinement with success-based learning-rate adaptation | NP=100, F=0.8, CR=0.7 |
| 4 | `de_harmony_search` | DE hybridized with Harmony Search (harmony memory, pitch adjustment, bandwidth decay 0.95) | HMS=20, HMCR=0.9, PAR=0.4, bw=0.5 |
| 5 | `de_local_search` | DE with gradient-estimation-based local search | NP=100 |
| 6 | `de_memetic_search` | Memetic DE with finite-difference gradient refinement | internally fixed parameters |
| 7 | `de_perturbation` | DE with adaptive, gradient-guided perturbation | NP=100, F=0.8, CR=0.7 |
| 8 | `de_plus` | Success-based self-adaptation of `F` and `CR` (adaptation rate 0.1) | NP=100 |
| 9 | `de_pso` | DE–PSO hybrid: random F∈[0.4,0.9], CR∈[0.6,1.0], velocity update (c₁=c₂=1.5, w=0.5) | dynamic population |
| 10 | `dynamic_pop_v2` | Per-individual F∈[0.5,2.0], CR∈[0.1,1.0] with dynamic population-size adaptation | NP_init=100 |

> **Note:** `de_memetic_search` exposes no external hyperparameters — its parameters are fixed inside the generated code. It is therefore excluded from the per-algorithm sensitivity analysis, which is itself an informative structural property of LLM-generated algorithms.

## Experimental Protocol

| Setting | Value |
|---|---|
| Benchmark suite | CEC2022 (12 functions: F1 unimodal, F2–F5 basic multimodal, F6–F8 hybrid, F9–F12 composition) |
| Benchmark implementation | `opfunu` v1.0.4 |
| Search domain | [−100, 100]^D |
| Dimensions | D = 10 and D = 20 |
| Independent runs | 30 per algorithm–function–dimension |
| Evaluation budget | 200,000 (10D) / 1,000,000 (20D) |
| Success criterion | error < 1e−8, where error = f_best − f_opt (clipped at 0) |
| **Total production runs** | **10 × 12 × 2 × 30 = 7,200** |
| Logging | IOHprofiler format via the `ioh` package (v0.3.22) `Analyzer` logger |

## Reproducing the Experiments

### 1. Production benchmark

Runs one algorithm over all 12 CEC2022 functions in both dimensions (30 runs each) and writes IOHprofiler logs plus a per-run CSV:

```bash
python benchmarking/ioh_production_runner.py --algorithm adeo
```

Repeat for each of the ten algorithm keys: `adeo`, `de_crossover`, `de_gradient_boost`, `de_harmony_search`, `de_local_search`, `de_memetic_search`, `de_perturbation`, `de_plus`, `de_pso`, `dynamic_pop_v2`.

Outputs:
- `production_results_<algorithm>.csv` — one row per run
- `<algorithm>_statistical_summary.csv` — descriptive statistics
- `ioh_data_all/<algorithm>/` — IOHprofiler logs for IOHanalyzer

> ⚠️ **Runtime warning.** The full benchmark is computationally expensive. Per-function wall-clock times range from a few minutes to several hours; the hybrid functions F7 and F8 at 20D take the longest (7–10 h each on the reference machine). Budget several days for the complete 7,200-run experiment, and run algorithms in parallel processes where possible.

### 2. Performance analysis

Import `ioh_data_all/` into [IOHanalyzer](https://iohanalyzer.liacs.nl/) to produce AOCC, ERT, ECDF/EAF curves, radar profiles, and performance heatmaps. Exported summaries used in the paper are in `results/`.

### 3. SHAP explainability

```bash
# Level 1 — per-algorithm hyperparameter sensitivity
python explainability/shap_hyperparameter_sensitivity_all.py

# Levels 2 & 3 — algorithm selection and error-driver attribution
python explainability/shap_production_analysis.py
```

Level 1 samples random hyperparameter configurations at a **reduced screening budget of 8,000 evaluations with 2 repetitions per sample** — a deliberate trade-off, since a full sweep at the production budget would multiply the cost by two orders of magnitude. Sample counts are defined at the top of each script.

### 4. Search Trajectory Networks

```bash
python stn/ADEO.py          # writes merged trace files
```

Trajectories log the best-so-far solution at initialization, every tenth generation, and at termination. Coordinates are discretized on a grid of resolution 10^(−SP), where

```
SP = 2 − floor(log10(D × (ub − lb)))
```

Traces from all 30 runs of an algorithm–function pair are merged into a single network and rendered with the Kamada–Kawai and Fruchterman–Reingold layouts.

### 5. Behavioural metrics

```bash
python behaviour/analysis.py
```

Computes ten trajectory-based descriptors per run: average nearest-neighbour distance (window 1000, sampled every 10th evaluation), coverage dispersion (10,000 uniform reference points), chunk-wise exploration/exploitation percentages (chunks of 500), average distance to best-so-far, intensification ratio (10% domain-width radius), average convergence rate, improvement rate, average improvement magnitude, longest no-improvement streak, and last-improvement fraction.

## Analysis Pipelines

### SHAP — three levels

| Level | Question | Model | Features → Target |
|---|---|---|---|
| **1** | Which of its own controls does each variant depend on? | RandomForestRegressor (300 trees) | variant hyperparameters, dimension, function → log(1+error) |
| **2** | What determines which variant is best? | RandomForestClassifier (300 trees) | (function, dimension) → best algorithm |
| **3** | What drives difficulty across the benchmark? | RandomForestRegressor (300 trees) | (algorithm, function, dimension) → log(1+error) |

Random Forests are used because TreeSHAP computes Shapley values *exactly* in polynomial time for tree ensembles, the relationships involved are non-linear over mixed feature types, and tree surrogates are the established choice in explainable benchmarking of iterative optimization heuristics.

> The surrogate models serve **attribution, not prediction** — they represent the structure of the benchmark data so that SHAP can decompose it. No train–test split is used, and the attributions describe the benchmark that was run rather than out-of-sample generalization.

## Key Findings

A condensed summary; see the paper for full analysis.

**1. Anytime performance barely separates the cohort.** Over the whole 10D suite, the ECDF area ranges only from 0.949 to 0.966 across ten structurally different algorithms — AOCC alone is a poor discriminator here, and a study reporting it in isolation would wrongly conclude the variants are near-equivalent.

**2. Fixed-target reliability separates them sharply.** Counting functions with a finite ERT in 10D: `de_harmony_search` 8/12, `de_pso` 6/12, `adeo` and `de_crossover` 5/12, `de_plus` 4/12, `de_memetic_search` 2/12 — while `de_gradient_boost`, `de_local_search`, `de_perturbation`, and `dynamic_pop_v2` reach the target on **no function at all**.

**3. The "best" algorithm is criterion-dependent.** `de_harmony_search` leads on AOCC and ERT breadth; `de_crossover` leads on per-run success rate (34.6% of runs vs 20.4%). A high anytime score and a high exact-hit rate reflect genuinely different behavioural profiles.

**4. The suite partitions into solvable and unsolved subsets.** Aggregated over all variants in 10D, the target is reached on F1 (51.7%), F3 (51.0%), F11 (31.0%), and F5 (28.7%), but essentially never on F2, F4, F6, F7, F8, F10, F12 — which explains the common ECDF ceiling near 0.885–0.90.

**5. Peak 10D performance and dimensional robustness are largely distinct properties.** Measured as growth in geometric-mean median error from 10D to 20D, the strongest 10D variants degrade most (`de_crossover` 7.2×, `adeo` 6.9×), while `de_memetic_search` (1.9×) and `de_harmony_search` (2.5×) scale best.

**6. Trajectory networks distinguish failure modes that error values cannot.** Two variants with comparable errors can fail in opposite ways: *dispersion without attraction* (30 disjoint components, no two runs ever meeting) versus *premature collapse* (the smallest network in the study). Both look like stagnation on a convergence curve.

**7. SHAP ranks landscape ≫ dimension > algorithm** as the drivers of error across the benchmark, and recovers each variant's mechanistic fingerprint from data — e.g. c₁ and c₂ emerge as the leading internal drivers for the DE–PSO hybrid.

## Data Description

| File | Contents |
|---|---|
| `production_results_<algo>.csv` | One row per run: Algorithm, Function_ID, Dimension, Run, Error, Success, Best_Fitness, Time |
| `all_algorithms_production_combined.csv` | All 7,200 production runs |
| `<algo>_statistical_summary.csv` | Mean, std, median, min, max, IQR of error and success rate per (function, dimension) |
| `AUC_ECDFEAF_MULTI.csv` | ECDF area (AUC) and AOCC per algorithm, 10D |
| `MultiERT-10D.csv` | Expected running time per function; `inf` = target not reached within budget |
| `STN_data/*.pdf` | 465 STN visualizations (FR and KK layouts); titles report nodes, edges, components |
| `ioh_data_all/<algo>/` | Raw IOHprofiler logs (`.dat` best-so-far trajectories + `.info` metadata) |
